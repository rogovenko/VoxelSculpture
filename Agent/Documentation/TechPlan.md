### 1.1 Чего в стеке сознательно нет

- **Физического движка.** Осколки (§7.5 GDD) — «только эффект», им достаточно баллистики из трёх строк: скорость, гравитация, время жизни. Rapier/cannon-es добавят вес бандла и ничего не дадут.
- **Моделей окружения.** Атлас трещин по-прежнему генерируется на Canvas2D. Мрамор глыбы — одна текстура, `assets/images/diorite.png`. Серые коробки арены без моделей.
- **State-менеджера.** Состояние игры — один объект домена плюс шина событий.
- **ECS.** Сущностей в прототипе ровно три вида, ECS здесь — оверинжиниринг.

## 2. Архитектура

Три слоя, где нижний не знает о верхних и о Three.js вообще.

```
domain/   чистый TS. Сетка, рейкаст, урон, оценка, события. Нет импортов three
  ↑
view/     Three.js. Рендер сетки, подсветка, осколки, камера, свет, пропы
  ↑
app/      Точка входа, игровой цикл, ввод, склейка слоёв
ui/       DOM-оверлеи, подписаны на события домена
```

Почему так, а не «всё в одном файле сцены»: GDD прямо просит заложить в архитектуру дешёвые вещи под будущий incremental — «луч из центра, DPS как число, типы вокселей, событие "клетка сломана"» (§12 GDD). Всё это живёт в домене. Плюс домен становится тестируемым без браузера — а именно в рейкасте, в физике игрока и в досягаемости слоёв будут баги.

### 2.2 Ключевые структуры данных

Сетка — плоские типизированные массивы, индекс `x + y * sx + z * sx * sy`. При максимуме 9×9×16 = 1296 клеток это меньше 8 КБ памяти, никаких чанков и октодеревьев не нужно.

```ts
// domain/types.ts
export const enum VoxelType {
  Air = 0,
  Marble = 1,
  Sculpture = 2,
}

export type Face = 'px' | 'nx' | 'py' | 'ny' | 'pz' | 'nz';

export interface HitResult {
  x: number;
  y: number;
  z: number;
  index: number;
  type: VoxelType.Marble | VoxelType.Sculpture;
  face: Face;
  distance: number;
}
```

```ts
// domain/VoxelGrid.ts (контракт)
export class VoxelGrid {
  readonly size: readonly [number, number, number];
  readonly type: Uint8Array; // VoxelType
  readonly hp: Float32Array; // текущее HP клетки
  readonly maxHp: Float32Array; // для нормализации стадии трещин и оценки

  marbleRemaining: number; // условие победы §8.1
  marbleDestroyed: number; // метрика §8.2

  indexOf(x: number, y: number, z: number): number;
  inBounds(x: number, y: number, z: number): boolean;
  typeAt(x: number, y: number, z: number): VoxelType;
  isSolid(x: number, y: number, z: number): boolean;
  removeAt(index: number): void;
}
```

Формат уровня — единая точка входа для процедурного креста сейчас и для `.vox` потом:

```ts
// domain/levels/LevelData.ts
export interface LevelData {
  version: 1;
  name: string;
  size: [number, number, number];
  /** индекс палитры MagicaVoxel -> семантика игры */
  materials: Record<number, 'marble' | 'sculpture'>;
  /** упакованные четвёрки x, y, z, paletteIndex */
  voxels: Int32Array;
}
```

Крест из §4.1 GDD генерируется кодом, но **отдаёт `LevelData`**, а не строит сетку напрямую. Это единственное, что нужно сделать сейчас, чтобы конвертер `.vox` на фазе 10 подключился без изменения игровой логики.

### 3.1 Урон не сбрасывается вообще

Изначально §7.4 GDD требовал сбрасывать трещины и прогресс HP при смене цели, и это противоречило и «царапине» из §12.3, и частичному урону в оценке из §8.2. Противоречие снято в самом GDD: **урон необратим для обоих типов вокселей** (§6.2, §7.4).

- **Мрамор:** HP не восстанавливается. Отпустил ЛКМ, отошёл, вернулся — долбишь дальше с того же места.
- **Оригинал:** так было с самого начала — клетка остаётся частично повреждённой и подкрашенной.

Следствия для кода: `ChiselSystem` не хранит текущую цель и не откатывает HP, а `stop()` только снимает флаг удержания. Следствие для баланса: сессия становится короче на величину «недодолбленных» клеток, зато метрика частичного урона из §8.2 наконец имеет смысл.

### 3.2 Время сессии — главный балансный риск

Победа требует снять **весь** мрамор (§8.1), поэтому длительность сессии равна `количество_мраморных_клеток × HP / DPS` и других рычагов нет.

| Сетка    | Мраморных клеток | HP клетки | При DPS 2.5 |
| -------- | ---------------- | --------- | ----------- |
| 7×7×12   | ~504             | 1.0       | ~3.4 мин    |
| 9×9×16   | ~1150            | 1.0       | ~7.7 мин    |
| 14×14×24 | ~4030            | 1.0       | ~27 мин     |

**Прочность задана на клетку и при дроблении вокселя намеренно не пересчитана по объёму.** Поделить её на восемь означало бы вернуть прежние 3.4 минуты, но клетка уходила бы за 0.05 с: ни стадий трещин, ни «подержал и отколол», а отдача камеры при двадцати сломах в секунду сливается в постоянную вибрацию. Решение принято в пользу ощущения отдельной клетки, и §11 GDD с этим расхождением сверен — там оно записано как известное.

Отсюда следует, что **длина сессии больше не сходится с §11 GDD** и это главный незакрытый долг баланса. Рычаги, в порядке правильности:

1. **AOE-резец из §12.7 GDD** — один слом снимает горсть клеток. Возвращает и время сессии, и смысл стадий трещин, и раздельные удары вместо вибрации. Единственный вариант, который ничего не портит.
2. **Победа не по последней клетке** — например, по доле снятого мрамора. Дешевле, но меняет §8.1.
3. **Сетка обратно мельче числом клеток** — отменяет само зерно, ради которого всё делалось.

Чего делать нельзя: поднимать DPS выше ~4 — удержание превратится в «один тап», что §11 GDD прямо запрещает.

### 3.3 Прочие решения, которых GDD не касается

- **Единицы:** масштаб задаёт игрок, а не воксель. Его габариты, дальность руки, высота шага и вся арена — **мировые константы**, ни одна из них не выражена через `voxelSize`. Поэтому воксель можно дробить как угодно (сейчас `CONFIG.grid.voxelSize = 0.25` при сетке 14×14×24): физика, ощущение движения и размер глыбы не меняются, меняется только зерно. Домен и рейкаст считают в **клетках**, физика и арена — в мировых единицах; перевод живёт в двух местах: `arena.glybaMin` + `voxelSize` (`CollisionWorld` и `Game`). Сетка центрирована по X и Z, растёт по Y вверх от пола арены (`y = 0`), цоколя под ней нет.
- **Масштаб группы вокселей:** `VoxelRenderer` работает в целых клетках, а мировой масштаб задаёт владелец через `scale`/`position` его группы. Осколки (`ShardFX`) при этом живут в сцене, а не внутри этой группы: их размер задан своим параметром конфига (`shards.size`), пусть и выраженным через воксель, а скорость и время жизни — мировые. Держать их в группе значило бы масштабировать заодно и разлёт, и это ровно та связка, из-за которой при первом дроблении вокселя эффекты уехали.
- **Ось вверх:** Y (стандарт Three.js). MagicaVoxel использует Z-up — пересчёт делает плагин Vite при импорте `.vox` (`voxToGame`), не рантайм игры.
- **Дельта времени:** `dt` клампится по `MAX_DT = 1/30`. Иначе фриз или переключение таба выдаст один кадр с огромным `dt`, который снесёт воксель мимо стадий трещин.
- **Урон:** непрерывный `hp -= dps * dt` (§7.3 GDD), стадия трещин — производная от `hp / maxHp`, дискретизированная на 8 шагов.
- **Рейкаст:** максимальная дистанция ограничена (`REACH`, порядка 5 клеток), луч всегда из глаза игрока через центр экрана, независимо от позиции курсора.

### 3.4 Точки расширения для правок «извне»

Проект правят не только те, кто знает его целиком. Поэтому три частые правки вынесены в отдельные швы: у каждой ровно один файл, куда надо дописать, и ноль знаний об остальном коде. Пошаговые инструкции — в `LevelAuthoring.md` и `SceneAuthoring.md`.

- **Фигура внутри глыбы** — `levels/shapeLevel.ts` собирает `LevelData` из предиката «клетка принадлежит фигуре». `crossLevel.ts` и `duckLevel.ts` — клиенты каталога: крест задаёт границы **долями габарита**, утка берёт клетки и RGB из `.vox`. Своя фигура — новый файл и одна строка в `catalog.ts`. У записи есть `size: 'small' | 'medium'`: на `small` арена не строит леса, сетка сейчас `8×12×10`. Запись без фабрики (`create: null`) видна, но выбрать её нельзя.
- **Декорации с коллизией** — `levels/props.ts`, массив `DECOR`. Попадает в `arena.boxes`, то есть сразу и в картинку, и в физику, и в тесты досягаемости. Второго списка геометрии нет намеренно: он бы разъехался с коллизией при первой правке.
- **Модель на месте коробки** — флаг `invisible` на `ArenaBox`. Коробка остаётся препятствием, но `blockout` её не рисует. Это единственный поддерживаемый способ поставить модель: коллизия по-прежнему описана раскладкой арены, а не геометрией меша. Меш-коллайдеров и поворотов физика не умеет и уметь не должна — сложная форма собирается из нескольких AABB.

Отладка сделана по тому же принципу: `ui/DebugMenu.ts` монтируется в меню паузы только при `import.meta.env.DEV` и даёт две вещи, ради которых иначе лезли бы в конфиг, — ваншот по мрамору (`ChiselSystem.setOneShot`) и «оставить один воксель» (`Game.keepSingleMarbleVoxel`). Ваншот сознательно не действует на оригинал: случайный кадр по кресту испортил бы ровно ту оценку, ради которой уровень и прогоняют быстро. Массовое снятие клеток идёт напрямую по сетке и рендереру, без событий домена: несколько тысяч всплесков осколков и отдач камеры положили бы кадр.

## 4. Технические решения по рендеру

### 4.1 Геометрия глыбы

**Один `InstancedMesh` единичных кубов, один инстанс на непустую клетку.** Per-instance атрибуты: `aType` (мрамор / скульптура), `aDamage` (0..1 для градиента §12.3), `aCrackStage` (0..8).

Обоснование выбора против greedy meshing: при 1296 клетках производительность не является фактором вообще. Инстансы дают то, чего меш-мерж не даёт бесплатно — **попиксельную привязку трещин и градиента повреждения к конкретной клетке** через атрибут инстанса. Ступенчатый воксельный силуэт, который §12.9 GDD называет фичей, сохраняется автоматически.

Удаление клетки — перестановка последнего инстанса на место удалённого и уменьшение `instanceCount` (swap-remove, O(1)), с обновлением карты `voxelIndex -> instanceSlot`. Полная перестройка буфера тоже была бы незаметна, но swap-remove проще отлаживать.

За этим стоит интерфейс:

```ts
export interface IVoxelRenderer {
  build(grid: VoxelGrid): void;
  removeVoxel(index: number): void;
  setDamage(index: number, damage01: number, crackStage: number): void;
  dispose(): void;
}
```

Когда глыбы вырастут и внутренние грани начнут стоить кадры, сюда встанет `GreedyMeshRenderer` без изменения игрового кода.

**Оптимизация «скрытые клетки»:** клетки, у которых все 6 соседей непрозрачны, невидимы. Пропускать их при билде можно, но тогда удаление соседа требует ленивого досоздания инстанса. Для прототипа **не делаем** — риск рассинхрона выше выгоды, которой при 1296 инстансах нет. Отмечено как задел.

### 4.2 Материал вокселя

Кастомный `ShaderMaterial` с полностью своими вершинным и фрагментным шейдерами и **захардкоженным освещением** (одно направление + ambient), без подключения к системе света Three.js. Патчинг `MeshLambertMaterial` через `onBeforeCompile` тут отвергнут сознательно: он требует строковой замены в чужих шейдер-чанках и ломается от версии к версии.

Материал делает следующее:

1. **Мрамор** — текстура `diorite.png` по мировой UV (пара осей от нормали грани), не на клетку. Иначе глыба снова читается как плитка. `colors.marble` — запас, если карты нет.
2. **Скульптура пока долбишь** — зелёный, по `aDamage` зелёный → жёлтый → алый (§12.3 GDD).
3. **После зачистки мрамора** — RGB из `.vox` (`aPaint`), если он был. Урон не стирается: поверх авторского цвета краснота, затемнение и трещины. На добитых клетках последняя стадия трещин возвращается в `revealPaint`.
4. **Оверлей трещин**: сэмпл атласа по стадии, UV грани куба, умножение (darken).

Затемнения рёбер в шейдере **нет**: клетку под прицелом рисует `HighlightBox`. Освещение сцены — `HemisphereLight` + один `DirectionalLight`; у глыбы своё `uLightDir`. Тени не включаем.

### 4.3 Атлас трещин

Генерируется процедурно на `<canvas>` при инициализации: 8 стадий, по 64×64, горизонтальной полосой в одну текстуру. Алгоритм — ветвящиеся ломаные линии от случайных точек, число и толщина линий растут со стадией; каждая стадия включает линии предыдущей, чтобы трещины «нарастали», а не мигали.

Фильтрация `NearestFilter` — дискретный minecraft-подобный вид (§7.4 GDD), плюс сразу видно, если UV поехали.

Позже атлас подменяется на нарисованный PNG без изменения шейдера.

### 4.4 Подсветка цели

`LineSegments` по `EdgesGeometry` куба, чёрный `LineBasicMaterial`, `depthTest: true`, масштаб `1.002` и `polygonOffset` — против z-fighting с гранями вокселя. Один переиспользуемый объект, при промахе просто `visible = false`. Позиция обновляется в том же кадре, что рейкаст, — «подсветка следует за прицелом мгновенно» (§6.3 GDD).

Рисуется и на мраморе, и на скульптуре — §6.3 GDD настаивает.

### 4.5 Осколки

Пул на ~200 мелких кубов в одном `InstancedMesh`. При разрушении мраморной клетки спавнится 6–10 осколков размером 0.15–0.3 вокселя:

- начальная скорость: наружу по нормали задетой грани + случайный конус + вверх;
- гравитация, лёгкое случайное вращение;
- время жизни 0.4–0.8 с (§11 GDD), к концу масштаб уходит в ноль;
- пола не касаются и не отскакивают — «физика осколков не геймплей» (§7.5 GDD).

Удар по скульптуре — отдельный, более скромный эффект: 3–4 частицы пыли без разлёта (§7.5 GDD).

Плюс микро-kick камеры на слом (§12.5 GDD): смещение на 0.02–0.05 unit с затуханием за 120 мс. Слабый, как просит §9 GDD.

### 4.6 Камера и перемещение

Камера от первого лица (§6.1 GDD) разделена на две части, чтобы движение осталось тестируемым без WebGL:

- `domain/PlayerBody` — габариты (0.95 × 2.95 world unit, то есть почти 4 × 12 нынешних вокселей), скорость, гравитация, прыжок, шаг на полвысоты колена, лазание по лестнице. Движение разрешается по осям раздельно (Y, затем X, затем Z), пересечение ищется бисекцией: одна и та же процедура работает и по вокселям, и по коробкам арены.
- `domain/CollisionWorld` — запросы «занято ли»: воксельная сетка через `VoxelGrid.isSolid` плюс список статических AABB арены, и отдельно «касаюсь ли лестницы».
- `view/PlayerCamera` — кладёт глаз, `yaw`/`pitch` (порядок Эйлера `YXZ`, иначе кренится горизонт), kick и FOV на `THREE.PerspectiveCamera`.

`OrbitControls` и собственный `CameraRig` не нужны: смотреть надо из глаза игрока, а не по дуге вокруг цели.

**Габариты не ровно круглые, а чуть меньше.** При точном совпадении с решёткой выдолбленный ровно в рост коридор не пропускал бы игрока: погрешность в один ULP уже задевает следующий слой клеток. Поэтому 0.95 × 2.95 вместо 1 × 3 — щель всё так же не проходима, а честный проход в свой рост работает без дребезга.

**Высота шага тоже мировая.** `stepHeight = 0.525` — это чуть больше двух нынешних вокселей, а не один, как было на крупной сетке. Привязать шаг к клетке значило бы, что при каждом дроблении сетки игрок начинает спотыкаться о всё более мелкие уступы: длина ноги от разрешения мрамора зависеть не может. Правило «на один воксель шагаем, на два нет» из §6.1 GDD переформулировано соответственно.

**Лестница — сплошная опора с дополнительной ролью.** `ArenaLayout.ladders` лежит отдельно от `boxes`, но в коллизию входит наравне с ними: сквозь лестницу не пройти. Отдельный список нужен ради второй роли — пока тело **касается** лестницы, гравитация отключена, а вертикальная скорость берётся из ввода. Именно касания, а не пересечения: в сплошную коробку тело попасть не может, поэтому `onLadder` раздувает запрос на `LADDER_GRIP` по горизонтали. Отсюда же берётся сиреневый цвет в `blockout`: лестница — единственная геометрия арены, с которой игрок взаимодействует, и она обязана читаться.

**Односторонность подъёма — следствие геометрии, а не правило в коде.** Лестницы стоят боковыми опорами «П», настил лежит между ними. Снаружи подъём свободен и заканчивается шагом на настил, изнутри упирается в настил снизу. Никакой проверки «с какой стороны игрок» писать не нужно, и это хорошо: такая проверка сломалась бы на углах.

**Верх опоры совпадает с настилом**, то есть вся верхушка «П» — одна плоскость. Расплата за это — `LADDER_GRIP` растянут и вниз по Y: иначе на последнем шаге подъёма тело оказывается ровно над опорой, теряет хват и съезжает обратно, так и не попав на настил.

**Раскладка арены — данные, а не константы вида.** `domain/levels/arena.ts` отдаёт списки коробок, по которым строится и картинка (`view/blockout`), и коллизия. Двух списков геометрии быть не должно: они разъедутся при первой правке, и игрок начнёт застревать в воздухе.

**Инвариант досягаемости.** Высота глаз, дальность руки и высота настила связаны арифметикой, и с лесами лишь с двух сторон это перестаёт быть одномерной задачей: часть верхней грани достаётся только с противоположных лесов. `arena.test.ts` проверяет две вещи — покрытие всех слоёв по вертикали и досягаемость **всей внешней оболочки** глыбы из позиций, где игрок физически может стоять. Дальше долбёжка идёт вглубь, то есть всегда ближе, поэтому оболочки достаточно. Если инвариант сломан, победа не срабатывает никогда, а игрок просто не находит последний блок.

**Просвет под настилом.** Настил лесов один и висит выше роста игрока. Второй ярус пришлось убрать: настил на удобной для рук высоте перекрывал проход к низу глыбы, а поднять его — значит потерять возможность пройти под первым.

ПКМ расширяет FOV вместо отъезда: от ног игрока отъезжать некуда, но жест «отошёл от станка» сохраняется (§12.2 GDD).

## 5. Ввод

```
Стартовый оверлей: клик «Начать» -> requestPointerLock()
Pointer lock активен:
  mousemove          -> yaw/pitch, всегда (в том числе во время долбёжки)
  WASD               -> MoveIntent.forward/strafe относительно взгляда
  Space              -> прыжок при PlayerBody.grounded (на лестнице не действует)
  W у лестницы       -> подъём: то же нажатие прижимает к лестнице
  Shift              -> спуск на лестнице (вне лестницы ничего не делает)
  C                  -> присед, рост × crouchScale; встать нельзя, если над головой потолок
  ЛКМ down           -> ChiselSystem.begin()
  ЛКМ hold           -> каждый кадр ChiselSystem.update(dt)
  ЛКМ up             -> ChiselSystem.stop(), урон остаётся на клетке
  ПКМ down/up        -> PlayerCamera.setPulledBack(bool), расширение FOV
  Esc                -> выход из lock -> пауза + «Продолжить»;
                       если мрамор уже снят — оверлей «Работа принята»
contextmenu          -> preventDefault (иначе ПКМ откроет меню браузера)
```

Подъём привязан к «вперёд», а не к отдельной кнопке, и это не только привычка по Minecraft: то же нажатие прижимает игрока к лестнице, поэтому хват не срывается сам собой. Спуск по этой логике не может быть «назад» — оно бы отодвигало от лестницы, — поэтому спуск на Shift. Присед — C, отдельно от спуска: рост и глаза множатся на `crouchScale`, встать под потолком нельзя. Ввод в эти правила не лезет: он отдаёт `forward`, `climbDown` и `crouch`, а решает `PlayerBody`.

Отпускание ЛКМ ничего не откатывает (§3.1). Тест `chiselSystem.test.ts` проверяет обратное тому, что было раньше: урон переживает `stop()`, смену цели и потерю луча, и накапливается между удержаниями.

Потеря pointer lock браузером (переключение окна) обрабатывается как Esc — иначе игра останется в состоянии «ЛКМ зажата» навсегда.

## 6. План реализации по фазам

Каждая фаза заканчивается работающей сборкой и явным критерием приёмки. Оценки — в днях работы, ориентировочные.

### Фаза 0 — Каркас проекта (0.5 д)

`npm create vite` с шаблоном `vanilla-ts`, `git init` с `.gitignore`, установка `three`, dev-зависимостей (`vitest`, `eslint`, `prettier`, `tweakpane`, `stats.js`), `tsconfig` в strict, конфиг ESLint, скрипты `dev / build / preview / test / lint / format`, README с инструкцией запуска. Пустая сцена: рендерер, обработка ресайза, `GameLoop` с clamp `dt`, `config.ts` со всеми числами §11 GDD.

**Приёмка:** `npm run dev` открывает страницу с очищенным цветным буфером и стабильными 60 fps; `npm run build` собирается без ошибок; `npm test` проходит (пусть на одном пустом тесте); `npm run lint` чистый.

### Фаза 1 — Доменный слой сетки (1 д)

`types.ts`, `LevelData` со валидатором, `VoxelGrid` с построением из `LevelData`, `crossLevel.ts` — генератор креста 9×9×16.

**Приёмка:** тесты на индексную арифметику, границы, `removeAt` со счётчиками; тест, что генератор креста даёт симметричную по X/Z форму, полностью скрытую внутри мрамора (ни одна клетка оригинала не имеет соседа-воздуха на старте — иначе §4.1 GDD «снаружи виден только светлый камень» нарушено).

### Фаза 2 — Рендер блок-аута (1 д)

`SceneRoot`, `lighting`, `blockout` (меши по коробкам арены, §4.1 GDD), `crackAtlas` (заготовка), `voxelMaterial` без трещин, `VoxelRenderer` на `InstancedMesh`. Камера пока статичная.

**Приёмка:** на экране серая воксельная глыба на полу серой арены, рядом леса с сиреневой лестницей; зелёного не видно ни с одного ракурса; рёбра клеток читаются; один draw call на глыбу.

### Фаза 3 — Камера, перемещение и ввод (1 д)

`arena`, `Aabb`, `CollisionWorld`, `PlayerBody`, `PlayerCamera`, `InputController`, `StartOverlay` с pointer lock, `Crosshair`, обработка Esc и потери lock, пауза.

**Приёмка:** обзор мышью по §6.1 GDD работает всегда, включая долбёжку; WASD везёт относительно взгляда, Space прыгает только с опоры; уступ ниже высоты шага берётся автоматически, выше — нет; в щель или коридор в один воксель игрок не просачивается; снаружи опоры лесов «вперёд» поднимает и на верхушке само выводит на настил, Shift опускает, без ввода игрок висит; изнутри подъём упирается в настил; сквозь лестницу не пройти; в мрамор и скульптуру войти нельзя, встать на них можно; за арену не выйти и в пустоту не упасть; вся внешняя оболочка глыбы достаётся хотя бы из одной позиции; под настилом лесов проходишь не пригибаясь; ПКМ плавно расширяет FOV и возвращает; Esc ставит на паузу и возвращает курсор; ПКМ не открывает контекстное меню.

### Фаза 4 — Рейкаст и подсветка (1 д)

`voxelRaycast` (DDA), `HighlightBox`, склейка в `Game`: каждый кадр луч из центра камеры → цель → позиция каркаса.

**Приёмка:** юнит-тесты рейкаста — попадание по осям, по диагонали, пролёт сквозь выдолбленные клетки до первой непрозрачной, промах мимо сетки, старт луча внутри сетки, ограничение по дистанции, корректная задетая грань. Визуально: рамка мгновенно следует за прицелом, исчезает в пустоте, рисуется и на зелёном.

### Фаза 5 — Долбёжка, HP и трещины (1.5 д)

`ChiselSystem` (накопление урона и события), генератор атласа трещин, атрибуты `aDamage`/`aCrackStage` в материале, поведение оригинала: не удаляется, градиент зелёный → жёлтый → алый, после «добития» трещины снимаются (§7.4 GDD).

**Приёмка:** тесты на необратимость урона по §6.2 GDD (переживает `stop()`, смену цели и потерю луча, накапливается между удержаниями), на `HP/DPS` как время разрушения, на неудаляемость оригинала. Визуально: удержание ЛКМ даёт нарастающие стадии трещин, слом за ~0.4 с, зелёная клетка от удара краснеет и остаётся на месте.

**Это фаза, на которой становится понятно, приятен ли кор.** Дальше идёт усиление ощущения, а не проверка гипотезы.

### Фаза 6 — Осколки и фидбек удара (1 д)

`ShardFX` (пул осколков, пыль для оригинала), микро-kick камеры на слом.

**Приёмка:** кусок читается как отколовшийся, а не исчезнувший; осколки уходят наружу и вниз и пропадают за 0.4–0.8 с; кадр не засоряется при быстрой долбёжке; прицеливаться в следующую клетку не мешает (§7.5 GDD).

### Фаза 7 — Победа, оценка, рестарт (1 д)

Условие победы (`marbleRemaining === 0`), `ScoreSystem` (повреждение оригинала с учётом частичного, снято мрамора, время с первого попадания), `WinOverlay` с цифрами и шуточным вердиктом по шкале §8.3 GDD, рестарт без перезагрузки страницы.

**Приёмка:** тесты `ScoreSystem` на границы шкалы вердиктов; зачистка срабатывает в кадр последней мраморной клетки (покраска `.vox`, счёт фиксируется); оверлей оценки — по Esc; рестарт полностью пересоздаёт домен и вид без утечек (проверяем счётчик `renderer.info.memory`).

Позже принято: сразу после зачистки игрок ещё ходит и смотрит заказ. Это не отменяет условие `marbleRemaining === 0`, меняется только момент показа UI.

### Фаза 8 — Тюнинг и сочность (1 д)

`DebugPanel` (Tweakpane: DPS, HP мрамора и оригинала, число стадий, размеры сетки, дальность руки, скорость и прыжок игрока, чувствительность мыши, FOV), балансный проход по §11 GDD, доводка читаемости глыбы и перекрестья, опциональный тонкий индикатор прогресса удара (§9 GDD).

**Приёмка:** сессия аккуратной игры укладывается в 1–3 минуты (§11 GDD); все игровые числа меняются из панели без пересборки; финальные значения зафиксированы в `config.ts`.

Осторожно с дальностью руки, размером вокселя, габаритами игрока и высотой настила: все четыре связаны с досягаемостью оболочки и с просветом под лесами (§4.6). Правка этих чисел обязана оставлять тест `arena.test.ts` зелёным, иначе уровень станет непроходимым молча.

### Фаза 9 — Аудио (0.5 д, опционально)

`AudioBus` на howler: ритмичный тук при удержании, жирный крэк на слом, неприятный чик по оригиналу, тишина/лёгкий эмбиент (§10 GDD). Смена тона удара, когда под прицелом зелёное (§12.5 GDD).

**Приёмка:** звук не блокирует старт при отсутствии файлов; кор читается и с выключенным звуком.

### Фаза 10 — Пайплайн `.vox` и фоновые пропы (1 д)

**Сделано для утки.** Плагин Vite + `vox.ts`: парсинг, Z-up → Y-up, занятые клетки → скульптура, RGB палитры в `LevelData.paint`, вскрытие после зачистки. Источник — `assets/vox/duck.vox`. Отдельный `tools/vox2level.ts` и JSON-снимок не понадобились.

Осталось из фазы: конвенция палитры для нескольких фигур, крест из `.vox` по желанию, `StaticProps` — статичные `.glb` фона через `GLTFLoader`.

**Приёмка утки:** правка `.vox` в MagicaVoxel после обновления страницы видна в уровне 1; после зачистки мрамора фигура окрашена, повреждения на месте.

**Суммарно: ~10 дней работы, из них 6 до момента «кор проверяем».**

## 8. Что считается готовой технической демкой

1. Серый блок-аут: пол, стены, леса с сиреневой лестницей с двух сторон на `medium`. Глыба `medium` 14×24×14 с крестом, `small` 8×12×10 с уткой из `.vox`. Обе стоят на полу.
2. Камера от первого лица по §6.1 GDD: WASD, прыжок, шаг на воксель, лазание по лестнице, коллизия с вокселями и блокаутом, расширение FOV по ПКМ.
3. Перекрестье, рейкаст по сетке, чёрный каркас целевой клетки.
4. Долбёжка удержанием ЛКМ: стадии трещин, `HP/DPS`, необратимый урон.
5. Оригинал не удаляется, краснеет по градиенту; после зачистки уровни из `.vox` показывают палитру, повреждения на месте.
6. Осколки как VFX, микро-kick камеры.
7. Зачистка при нулевом остатке мрамора, осмотр заказа, экран оценки по Esc с тремя метриками и вердиктом, рестарт.
8. Стабильные 60 fps, сборка деплоится как статика.
9. Юнит-тесты домена зелёные.
10. `LevelData` как единственный вход для геометрии уровня.

## 9. Задел, который не стоит нам ничего

Заложено архитектурой, но не реализовано — чтобы прототип «не закрыл двери» (§13 GDD):

- **DPS как одно число в конфиге** → апгрейды инструмента.
- **События домена** → квесты, статистика, престиж, звук, аналитика.
- **`IVoxelRenderer`** → greedy meshing для больших глыб.
- **`LevelData` + палитра + `.vox`** → новые силуэты из MagicaVoxel (§12.6 GDD): утка уже так живёт, следующая фигура — файл и строка в каталоге.
- **`materials` как маппинг, а не enum** → третий тип клетки (хрупкий камень, жила) добавляется данными.
- **`ChiselSystem` с целевым набором клеток, а не одной** → AOE-удар 2×1 и сквозной удар (§12.7 GDD).
- **`ScoreSystem`, возвращающий метрики отдельно от вердикта** → звёзды и ранги (§12.4 GDD).
